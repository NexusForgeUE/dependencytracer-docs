Installation

Dependency Tracer 1.1.0 prend en charge Unreal Engine 5.5, 5.6, 5.7 et 5.8 sous Windows 64 bits. Installez le paquet correspondant à la version mineure de votre moteur.

Installer depuis Fab

  1. Trouvez Dependency Tracer dans votre bibliothèque Fab du lanceur Epic Games et installez-le pour le moteur correspondant.
  2. Ouvrez votre projet. Dans Edit > Plugins, recherchez Dependency Tracer et activez-le si nécessaire.
  3. Redémarrez l'éditeur, puis ouvrez Tools > Dependency Tracer.

Installation manuelle depuis les sources

  1. Fermez Unreal Editor. Ne conservez qu'une installation du plugin : une ancienne copie dans le projet peut prendre le pas sur une installation dans le moteur.
  2. Placez le dossier DependencyTracer de l'archive dans le répertoire Plugins de votre projet. Le descripteur doit se trouver au chemin indiqué ci-dessous.
  3. Un paquet source nécessite les outils de compilation C++ pris en charge par votre version exacte du moteur. Compilez la cible éditeur du projet ou compilez le plugin avec l'outil BuildPlugin d'Unreal avant de l'installer.
  4. Ouvrez le projet, activez Dependency Tracer si nécessaire, redémarrez l'éditeur et ouvrez Tools > Dependency Tracer.

Votre première analyse

Commencez par une partie familière de votre projet. Enregistrez d'abord les ressources modifiées afin que les tailles des paquets sur disque reflètent leur dernier état enregistré. L'espace de travail s'ouvre initialement sur Dependency Tree ; passez à Overview après l'analyse. Ce guide conserve les libellés des boutons en anglais pour correspondre à l'interface du plugin.

  1. Choisissez le contenu à analyser. Ouvrez Project Settings > Plugins > Dependency Tracer. Laissez Analysis Roots sur /Game pour le projet ou choisissez un dossier plus restreint, comme /Game/Characters.
  2. Analysez votre projet. Ouvrez Tools > Dependency Tracer et cliquez sur Scan project. Attendez la fin de l'analyse. L'audit Blueprint facultatif s'exécute lorsque vous choisissez Scan + audit ou Run Blueprint Audit.
  3. Commencez par Overview. Vérifiez le nombre de ressources analysées, les tailles du contenu, les types de ressources et les plus grandes empreintes des ressources racines.
  4. Suivez une ressource lourde. Ouvrez Dependency Tree, choisissez-la avec Find asset ou sélectionnez-la dans le Content Browser et cliquez sur Use selected. Sélectionnez des cartes pour examiner leurs tailles et leurs références.
  5. Examinez les candidates. Ouvrez Unused Assets. Utilisez Browse et Open pour vérifier le rôle d'une ressource avant de la modifier.
  6. Conservez le résultat. Lancez Migration Audit lors de la préparation d'une mise à niveau, puis exportez en CSV ou JSON pour examiner le résultat.

Si vous modifiez des ressources ou des paramètres, lancez une nouvelle analyse. Utilisez Reload map lorsque la carte indique que son instantané provient d'une analyse précédente.

Périmètre et ressources racines

Le périmètre désigne l'ensemble des ressources à examiner. Une ressource racine est un point de départ considéré comme utilisé ; les ressources accessibles par ses références fortes ou souples sont conservées par l'analyse du contenu inutilisé.

  • Analysis Roots : chemins de contenu inclus dans l'analyse. La valeur par défaut est /Game.
  • Excluded Folders : chemins exclus de l'analyse, même lorsqu'ils se trouvent dans un dossier inclus.
  • Additional Root Folders : dossiers dont les ressources doivent être considérées comme utilisées, y compris le contenu chargé dynamiquement par votre jeu.
  • Include Plugin Content / Include Engine Content : extension facultative du périmètre. Les deux options sont désactivées par défaut.

Utilisez des chemins de paquets Unreal comme /Game/Characters plutôt que des chemins de dossiers Windows. Les ressources racines proviennent également des configurations prises en charge pour les cartes, l'empaquetage et la gestion des ressources. Toutes les cartes du périmètre sont considérées comme des racines. Si Cook All est activé dans votre configuration d'empaquetage, toutes les ressources du périmètre sont considérées comme utilisées et la liste des ressources inutilisées peut être vide.

Additional Root Folders ajoute des racines à préserver ; ce paramètre n'élargit pas le périmètre d'analyse. Incluez également un dossier dans Analysis Roots si vous souhaitez analyser entièrement son contenu.

Déclarez explicitement le contenu dynamique. Les chemins assemblés en C++, les chaînes lues depuis un fichier ou les systèmes externes d'exécution peuvent ne pas apparaître comme des références dans l'Asset Registry. Ajoutez les dossiers appropriés à Additional Root Folders et vérifiez les chemins de chargement de votre jeu.

L'analyse vérifie de nouveau les candidates isolées dans l'intégralité de l'Asset Registry, y compris les références provenant de l'extérieur du périmètre choisi. Cela augmente le niveau de confiance, sans permettre de découvrir toutes les références dynamiques à l'exécution.

Vue d'ensemble du projet

Overview résume la dernière analyse terminée. Commencez ici pour choisir la famille de ressources ou la ressource racine qui mérite votre attention.

  • Contenu analysé : tailles connues des paquets sur disque dans le périmètre configuré, avec le nombre de ressources et d'entrées ignorées.
  • Taille par type de ressource : les types les plus volumineux, pondérés selon leur part des octets connus analysés.
  • Plus grandes empreintes des racines : ressources racines dont l'ensemble des dépendances transitives par références fortes est volumineux.
  • Résumé des ressources inutilisées : nombre de candidates, nombre d'éléments à examiner manuellement et taille potentiellement récupérable. Cette taille additionne les tailles connues des candidates finalement classées Safe to delete.

Les tailles inconnues des paquets sont exclues des totaux de tailles connues. Ces chiffres représentent le périmètre de l'analyse ; ils ne correspondent pas à la taille de l'ensemble du dossier de votre projet.

Ressources inutilisées

Examinez les ressources inaccessibles depuis les racines détectées comme utilisées. Chaque entrée indique le type de ressource, sa taille propre connue, le niveau de confiance et le nombre de ressources qui y font référence.

Utilisez Top roots pour examiner les ressources racines dont l'empreinte totale par références fortes est importante. Utilisez By type pour voir quels types de ressources représentent le plus d'octets de paquets connus.

La recherche de taille utilise d'abord les tailles de paquets de l'Asset Registry et, à défaut, la taille du fichier de paquet enregistré dans le système de fichiers. Ces tailles servent d'indicateur du poids du build. La cuisson, la compression, la plateforme cible et les paramètres d'empaquetage peuvent produire une taille distribuée différente. Mesurez un build après cuisson si vous avez besoin de connaître sa taille réelle de distribution.

Arbre des dépendances

  1. Choisissez une ressource racine avec Find asset, sélectionnez une ressource dans le Content Browser et cliquez sur Use selected, ou saisissez son chemin de paquet et cliquez sur Load map.
  2. Choisissez Dependencies pour suivre les ressources auxquelles elle fait référence, ou Referencers pour examiner celles qui y font référence.
  3. Filtrez la carte avec Hard + Soft, Hard only ou Soft only.
  4. Sélectionnez une carte. Dans l'inspecteur à droite, consultez la taille propre et la taille totale, les compteurs de références, le poids des dépendances visibles et les constats de migration enregistrés.
  5. Utilisez Open Blueprint ou Open asset, Show in browser, Copy path et Focus asset pour poursuivre votre examen.

Lire les lignes

Les lignes continues couleur laiton représentent les références fortes. Les lignes en pointillés bleu-gris représentent les références souples. Les flèches suivent le sens réel des références dans les vues des dépendances comme dans celles des ressources référençantes. Les points identifient les embranchements partagés ; une interruption d'un tracé en pointillés à un croisement ne représente pas une connexion.

Les références souples permettent d'éviter une dépendance forte directe, mais les ressources chargées par leur intermédiaire peuvent rester nécessaires à l'exécution. La taille totale affichée et la répartition du poids concernent les dépendances fortes.

Audit de migration

Le Migration Readiness Report est inclus dans Dependency Tracer 1.1.0. Il vous aide à préparer la structure de vos Blueprints avant une migration du moteur.

  1. Configurez les racines d'analyse et les exclusions pour la couche Blueprint que vous souhaitez examiner.
  2. Ouvrez Migration Audit. Cliquez sur Run Blueprint Audit ou utilisez Scan + audit dans l'en-tête.
  3. Consultez le nombre de Blueprints inspectés et trouvés, ainsi que les éventuels échecs d'inspection. Examinez d'abord Blockers, puis Warnings et Info.
  4. Sélectionnez un constat pour lire ses éléments justificatifs, l'identifiant stable de sa règle, la structure du Blueprint et l'étape suivante recommandée. Utilisez Open Blueprint ou Show in Content Browser pour examiner la ressource.
  5. Exportez le résultat, effectuez les modifications adaptées à votre projet, compilez et testez manuellement, puis relancez l'audit.

Vérifier d'abord la couverture

  • No Blueprint audit : la dernière analyse normale n'incluait pas l'audit facultatif.
  • No Blueprints in scope : vérifiez les racines et les exclusions configurées si ce résultat est inattendu.
  • Inspection failures : certaines ressources n'ont pas pu être lues ; la couverture du rapport est partielle.
  • Completed : l'inspection et l'analyse prévues sont terminées. Cela ne prouve pas la compatibilité avec un moteur de destination.

L'inspection des Blueprints s'exécute sur demande et charge en mémoire les ressources du périmètre. Elle lit leur état de compilation actuel en mémoire ; elle ne lance aucune compilation, ne change pas leur classe parente, ne les reconstruit pas, ne les supprime pas et ne les enregistre pas explicitement. Le chargement par le moteur peut modifier l'état en mémoire, et l'audit ne l'enregistre pas silencieusement ni n'efface un indicateur de modification existant.

Testez la migration réelle du moteur sur une copie du projet. Ce rapport repère des problèmes structurels actuels et des points à examiner. Les nouvelles modifications de l'API du moteur, les changements de sérialisation, le comportement du C++ et les références chargées dynamiquement doivent toujours être testés dans la version de destination.

Référence des règles d'audit

Blockers signale un problème actuel ou une lacune de l'audit de préparation. Warnings comprend des heuristiques structurelles qui méritent un examen. Info identifie les fournisseurs à vérifier pour le moteur de destination.

Le couplage exclut les autoréférences. Les vérifications de couplage et de cycles utilisent les liens forts directs entre Blueprints du périmètre audité ; les liens souples, les Blueprints hors périmètre et les liens passant par d'autres types de ressources sont exclus de ces vérifications. Les classes natives ne sont pas comptées comme des ancêtres Blueprint. Les vérifications des fournisseurs de plugins inspectent également les classes parentes natives et les appels.

Un seuil est une invitation à examiner la structure, et non une limite de compatibilité. Modifiez les valeurs par défaut dans les paramètres du projet selon votre architecture ; les exports enregistrent les valeurs réellement utilisées.

Les chemins relatifs du répertoire des rapports sont résolus depuis le dossier du projet. Les paramètres de chemins de contenu utilisent les chemins de paquets Unreal. Relancez une analyse annulée avant de tirer des conclusions sur un nouveau périmètre.

Exports CSV et JSON

  1. Terminez l'analyse. Exécutez d'abord l'audit Blueprint facultatif si vous souhaitez inclure des constats de migration dans l'export.
  2. Utilisez Export dans l'en-tête, ou Export CSV / Export JSON dans Migration Audit.
  3. Consultez le chemin exporté dans l'interface. Les actions d'export de Migration Audit copient également ce chemin dans le presse-papiers.
  4. Les fichiers se trouvent dans <Project>/Saved/DependencyTracer/, ou dans le répertoire configuré par Report Export Dir.

Les deux formats exportent le rapport d'analyse, y compris ses données d'audit disponibles. Un export d'audit ne se limite pas aux lignes visibles avec la recherche ou le filtre de gravité actuels.

  • CSV : examinez les sections du rapport dans un tableur ou partagez-les pour vérification.
  • JSON : conservez un instantané structuré pour effectuer des comparaisons ou l'utiliser avec vos propres outils.

Les données de migration comprennent la couverture, les constats, les métriques par Blueprint et les seuils réellement utilisés. Le CSV contient plusieurs sections de rapport ; le JSON utilise la version de schéma 1.0. Aucun des deux exports n'inclut le graphe complet des dépendances. Comparez des rapports utilisant le même périmètre et les mêmes paramètres ; des changements de périmètre peuvent expliquer des variations dans les totaux ou les constats.

Une analyse normale ultérieure remplace le résultat de l'audit par une analyse dont l'audit est désactivé. Une annulation ou un échec conserve le dernier rapport terminé. Après avoir rouvert l'éditeur, lancez une nouvelle analyse.

Dépannage

Dependency Tracer n'apparaît pas dans Tools

Activez le plugin dans Edit > Plugins et redémarrez l'éditeur. Vérifiez que son descripteur se trouve directement dans le bon dossier de plugin et que le paquet correspond à votre version du moteur. Une installation manuelle depuis les sources nécessite une chaîne d'outils C++ compatible avec le moteur et une compilation réussie de l'éditeur.

L'analyse est vide ou un dossier manque

Vérifiez Analysis Roots et Excluded Folders. Utilisez un chemin de paquet comme /Game/Characters. Activez le contenu des plugins si le périmètre souhaité le nécessite, puis lancez une nouvelle analyse.

Une taille est inconnue ou inférieure à celle attendue

Enregistrez la ressource et relancez l'analyse. Le résultat utilise les tailles connues des paquets sur disque de l'Asset Registry. Les tailles non enregistrées ou inconnues peuvent être omises ; un parcours incomplet peut produire une borne inférieure. La sortie après cuisson peut différer des tailles des paquets enregistrés.

Ma candidate inutilisée est en réalité chargée par le jeu

Vérifiez les chemins dynamiques et les systèmes externes de chargement. Ajoutez les dossiers concernés à Additional Root Folders et relancez l'analyse. L'analyse des références ne peut pas déduire tous les chargements à l'exécution fondés sur des chaînes de caractères.

La carte des dépendances affiche d'anciens résultats

Attendez la fin de la nouvelle analyse, puis cliquez sur Reload map. Vérifiez la racine sélectionnée et le filtre de références fortes ou souples. Les limites d'affichage peuvent omettre des liens ; centrez la vue sur un autre nœud pour poursuivre l'exploration.

L'audit de migration indique qu'aucun audit n'a été exécuté

Un Scan project normal n'inspecte pas les graphes Blueprint. Ouvrez Migration Audit et utilisez Run Blueprint Audit ou Scan + audit.

L'inspection d'un Blueprint a échoué

Ouvrez la ressource manuellement et vérifiez les classes parentes manquantes, les fournisseurs et les problèmes de paquets. Résolvez-les et relancez l'audit. En attendant, la couverture est partielle.

Aucun constat n'est visible

Effacez la recherche et activez tous les filtres de gravité. Vérifiez le nombre de Blueprints inspectés et trouvés, ainsi que le périmètre. Un audit terminé sans constat signifie que ses règles actuelles n'en ont trouvé aucun ; il ne certifie pas une future migration du moteur.

Un rapport n'a pas pu être exporté

Attendez la fin de l'analyse. Vérifiez le répertoire de sortie configuré et les autorisations d'écriture, puis consultez Window > Developer Tools > Output Log pour lire les messages de Dependency Tracer.

Unreal signale des modules manquants ou incompatibles

Choisissez l'archive correspondant à la version mineure exacte du moteur et recherchez d'éventuelles installations dupliquées du plugin. Les paquets sources doivent être compilés avec une chaîne d'outils C++ compatible. N'utilisez pas de DLL provenant d'une autre version du moteur dans l'installation.

Questions fréquentes

Le plugin supprime-t-il ou réécrit-il mes ressources ?

Unused Assets présente des candidates et des actions de navigation dans l'éditeur. L'inspection des Blueprints charge les ressources, mais ne les compile ni ne les enregistre explicitement. Les modifications et le nettoyage font partie de votre démarche de vérification distincte.

La taille récupérable affichée garantit-elle l'espace économisé ?

Il s'agit de la taille connue des paquets des candidates à examiner. Vérifiez leur utilisation avant toute suppression. Les dépendances, la cuisson et la compression peuvent influer sur le contenu réel d'un build distribué.

Puis-je additionner les tailles des plus grandes ressources racines ?

Plusieurs racines peuvent partager les mêmes dépendances. Additionner leurs tailles totales compte ces paquets partagés plusieurs fois ; utilisez les totaux par type ou un build mesuré pour obtenir un autre point de vue.

Un audit sans constat garantit-il la réussite de la migration ?

Non. Le rapport examine la structure actuelle des Blueprints et leur état en mémoire. Validez une copie du projet dans le véritable moteur de destination et testez son code C++, ses fournisseurs, son contenu et son comportement.

Le rapport de préparation à la migration est-il inclus ?

Oui. Il est inclus dans Dependency Tracer 1.1.0, aux côtés des outils existants pour les dépendances et les tailles.

Mon jeu empaqueté a-t-il besoin de Dependency Tracer ?

Le module du plugin est réservé à l'éditeur. Son interface d'inspection ne s'exécute pas dans le jeu empaqueté.

L'analyse nécessite-t-elle un service en ligne ?

L'analyse du projet s'exécute localement dans Unreal Editor. Les rapports CSV et JSON sont écrits dans le répertoire local choisi.

Le projet d'exemple et les captures font-ils partie de mon analyse ?

Les captures montrent un projet de démonstration créé spécialement. Votre analyse utilise les ressources de votre projet configurées par vos soins. Les tailles et constats d'exemple de ce guide ne sont pas des résultats prédéfinis injectés dans le plugin.

Version et assistance

Ce guide couvre Dependency Tracer 1.1.0 pour Unreal Engine 5.5, 5.6, 5.7 et 5.8 sous Windows 64 bits.

Contenu de la version 1.1.0

L'interface Project Atlas avec ses cartes de dépendances et son inspecteur, les tracés des références fortes et souples, l'examen du contenu inutilisé, les rapports de taille par racine et par type, l'export CSV/JSON et le Blueprint Migration Readiness Report.

La compatibilité avec le moteur a été vérifiée avec UE 5.5.4, 5.6.1, 5.7.4 et 5.8.0 sous Win64. L'exécution sur Mac et Linux n'a pas été vérifiée dans l'environnement de validation de cette version.

Signaler un problème

Contactez nexusforgeuesupport@gmail.com.

Indiquez vos versions d'Unreal Engine et du plugin, l'onglet sélectionné, les racines et exclusions d'analyse, le message exact et les étapes permettant de reproduire le problème. Pour un problème de graphe, ajoutez le filtre de références fortes ou souples et une capture en taille réelle. Pour un problème d'audit, indiquez l'identifiant de règle et la couverture.

Ne partagez que les parties pertinentes des rapports et des journaux ; ils peuvent contenir des chemins et des noms de ressources du projet.
