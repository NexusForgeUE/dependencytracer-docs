Installation

Dependency Tracer 1.1.0 unterstützt Unreal Engine 5.5, 5.6, 5.7 und 5.8 unter Windows 64-Bit. Installieren Sie das Paket für die Minor-Version Ihrer Engine.

Über Fab installieren

  1. Suchen Sie Dependency Tracer in Ihrer Fab-Bibliothek im Epic Games Launcher und installieren Sie es für die passende Engine.
  2. Öffnen Sie Ihr Projekt. Suchen Sie unter Edit > Plugins nach Dependency Tracer und aktivieren Sie das Plugin bei Bedarf.
  3. Starten Sie den Editor neu und öffnen Sie anschließend Tools > Dependency Tracer.

Manuelle Installation aus dem Quellcode

  1. Schließen Sie den Unreal Editor. Behalten Sie nur eine Installation des Plugins: Eine ältere Kopie im Projekt kann Vorrang vor einer Engine-Installation haben.
  2. Legen Sie den Ordner DependencyTracer aus dem Archiv im Verzeichnis Plugins Ihres Projekts ab. Die Deskriptordatei muss sich im unten gezeigten Pfad befinden.
  3. Ein Quellcodepaket erfordert die C++-Build-Werkzeuge, die von Ihrer genauen Engine-Version unterstützt werden. Bauen Sie das Editor-Target des Projekts oder bauen Sie das Plugin vor der Installation mit Unreals Werkzeug BuildPlugin.
  4. Öffnen Sie das Projekt, aktivieren Sie bei Bedarf Dependency Tracer, starten Sie den Editor neu und öffnen Sie Tools > Dependency Tracer.

Ihr erster Scan

Beginnen Sie mit einem vertrauten Teil Ihres Projekts. Speichern Sie geänderte Assets zuerst, damit die Paketgrößen auf dem Datenträger ihrem zuletzt gespeicherten Zustand entsprechen. Die Arbeitsoberfläche öffnet zunächst Dependency Tree; wechseln Sie nach dem Scan zu Overview. Diese Anleitung belässt Schaltflächenbeschriftungen auf Englisch, damit sie zur Plugin-Oberfläche passen.

  1. Wählen Sie die zu scannenden Inhalte. Öffnen Sie Project Settings > Plugins > Dependency Tracer. Belassen Sie Analysis Roots für das gesamte Projekt auf /Game oder wählen Sie einen kleineren Ordner wie /Game/Characters.
  2. Scannen Sie Ihr Projekt. Öffnen Sie Tools > Dependency Tracer und klicken Sie auf Scan project. Warten Sie, bis der Scan abgeschlossen ist. Die optionale Blueprint-Prüfung wird ausgeführt, wenn Sie Scan + audit oder Run Blueprint Audit wählen.
  3. Beginnen Sie mit Overview. Prüfen Sie die Anzahl gescannter Assets, die Inhaltsgrößen, die Asset-Typen und die größten Speicherbedarfe der Wurzel-Assets.
  4. Verfolgen Sie ein großes Asset. Öffnen Sie Dependency Tree und wählen Sie das Asset mit Find asset aus oder markieren Sie es im Content Browser und klicken Sie auf Use selected. Wählen Sie Karten aus, um ihre Größen und Referenzen zu untersuchen.
  5. Prüfen Sie die Kandidaten. Öffnen Sie Unused Assets. Prüfen Sie mit Browse und Open den Zweck eines Assets, bevor Sie es ändern.
  6. Halten Sie das Ergebnis fest. Führen Sie zur Vorbereitung eines Upgrades Migration Audit aus und exportieren Sie anschließend CSV oder JSON zur Prüfung.

Wenn Sie Assets oder Einstellungen ändern, führen Sie einen neuen Scan aus. Verwenden Sie Reload map, wenn die Karte anzeigt, dass ihr Snapshot aus einem früheren Scan stammt.

Analysebereich und Wurzel-Assets

Der Analysebereich umfasst die zu untersuchenden Assets. Ein Wurzel-Asset ist ein Ausgangs-Asset, das als verwendet gilt; Assets, die über seine harten oder weichen Referenzen erreichbar sind, werden bei der Analyse ungenutzter Inhalte beibehalten.

  • Analysis Roots: Inhaltspfade, die in die Analyse einbezogen werden. Der Standard ist /Game.
  • Excluded Folders: Pfade, die von der Analyse ausgenommen werden, selbst wenn sie innerhalb eines einbezogenen Ordners liegen.
  • Additional Root Folders: Ordner, deren Assets als verwendet gelten sollen, einschließlich Inhalten, die Ihr Spiel dynamisch lädt.
  • Include Plugin Content / Include Engine Content: optionale Erweiterung des Analysebereichs. Beide Optionen sind standardmäßig ausgeschaltet.

Verwenden Sie Unreal-Paketpfade wie /Game/Characters statt Windows-Ordnerpfaden. Wurzel-Assets ergeben sich auch aus der unterstützten Map-, Packaging- und Asset-Verwaltungskonfiguration. Alle Maps im Analysebereich gelten als Wurzel-Assets. Ist Cook All in Ihrer Packaging-Konfiguration aktiviert, gelten alle Assets im Analysebereich als verwendet und die Liste ungenutzter Assets kann leer sein.

Additional Root Folders fügt Wurzel-Assets hinzu, deren Inhalte erhalten bleiben sollen; es erweitert nicht den Scanbereich. Nehmen Sie einen Ordner auch in Analysis Roots auf, wenn Sie seine Inhalte vollständig analysieren möchten.

Geben Sie dynamische Inhalte ausdrücklich an. In C++ zusammengesetzte Pfade, aus Dateien gelesene Zeichenketten oder externe Laufzeitsysteme erscheinen möglicherweise nicht als Referenzen in der Asset Registry. Fügen Sie die entsprechenden Ordner zu Additional Root Folders hinzu und überprüfen Sie die Ladepfade Ihres Spiels.

Der Scanner prüft isolierte Kandidaten erneut anhand der gesamten Asset Registry, einschließlich Referenzen von außerhalb des gewählten Analysebereichs. Das verbessert die Aussagekraft, kann aber nicht jede dynamische Laufzeitreferenz aufdecken.

Projektübersicht

Overview fasst den zuletzt abgeschlossenen Scan zusammen. Beginnen Sie hier, um die Asset-Gruppe oder das Wurzel-Asset auszuwählen, das Sie näher untersuchen möchten.

  • Gescannte Inhalte: bekannte Paketgrößen auf dem Datenträger im konfigurierten Analysebereich, mit der Anzahl der Assets und übersprungenen Einträge.
  • Größe nach Asset-Typ: die größten Typen, gewichtet nach ihrem Anteil an den bekannten gescannten Bytes.
  • Größter Speicherbedarf der Wurzel-Assets: Wurzel-Assets mit umfangreichen transitiven Abhängigkeiten durch harte Referenzen.
  • Zusammenfassung ungenutzter Assets: Anzahl der Kandidaten, Anzahl der manuell zu prüfenden Einträge und potenziell freigebbare Größe. Diese Größe summiert die bekannten Größen der abschließend als Safe to delete eingestuften Kandidaten.

Unbekannte Paketgrößen werden nicht in die Summen bekannter Größen einbezogen. Diese Zahlen beziehen sich auf den Analysebereich; sie entsprechen nicht der Größe Ihres vollständigen Projektordners.

Messen Sie einen Build nach dem Cooking, wenn Sie seine tatsächliche Auslieferungsgröße benötigen.

Abhängigkeitsbaum

  1. Wählen Sie ein Wurzel-Asset mit Find asset, markieren Sie ein Asset im Content Browser und klicken Sie auf Use selected oder geben Sie seinen Paketpfad ein und klicken Sie auf Load map.
  2. Wählen Sie Dependencies, um den referenzierten Assets zu folgen, oder Referencers, um Assets zu untersuchen, die darauf verweisen.
  3. Filtern Sie die Karte mit Hard + Soft, Hard only oder Soft only.
  4. Wählen Sie eine Karte. Lesen Sie im Inspektor rechts die direkte Größe und die Gesamtgröße, die Referenzzähler, den Speicherbedarf sichtbarer Abhängigkeiten und die aufgezeichneten Migrationsbefunde.
  5. Setzen Sie Ihre Untersuchung mit Open Blueprint oder Open asset, Show in browser, Copy path und Focus asset fort.

Die Linien lesen

Durchgezogene messingfarbene Linien stehen für harte Referenzen. Gestrichelte blaugraue Linien stehen für weiche Referenzen. In beiden Ansichten, für Abhängigkeiten und referenzierende Assets, folgen die Pfeile der tatsächlichen Referenzrichtung. Punkte markieren gemeinsame Verzweigungen; eine Lücke in einer gestrichelten Linie an einer Kreuzung ist keine Verbindung.

Weiche Referenzen können eine direkte harte Abhängigkeit vermeiden, doch die darüber geladenen Assets können zur Laufzeit trotzdem benötigt werden. Die angezeigte Gesamtgröße und die Aufschlüsselung des Speicherbedarfs beziehen sich auf harte Abhängigkeiten.

Migrationsprüfung

Der Migration Readiness Report ist in Dependency Tracer 1.1.0 enthalten. Er hilft Ihnen, Ihre Blueprint-Struktur vor einer Engine-Migration vorzubereiten.

  1. Konfigurieren Sie die Analysebereiche und Ausschlüsse für die Blueprint-Ebene, die Sie untersuchen möchten.
  2. Öffnen Sie Migration Audit. Klicken Sie auf Run Blueprint Audit oder verwenden Sie Scan + audit in der Kopfzeile.
  3. Lesen Sie die Anzahl untersuchter und gefundener Blueprints sowie mögliche fehlgeschlagene Untersuchungen. Prüfen Sie zuerst Blockers, dann Warnings und Info.
  4. Wählen Sie einen Befund, um seine Belege, die stabile Regel-ID, die Blueprint-Struktur und den empfohlenen nächsten Schritt zu lesen. Verwenden Sie Open Blueprint oder Show in Content Browser, um das Asset zu untersuchen.
  5. Exportieren Sie das Ergebnis, nehmen Sie die für Ihr Projekt geeigneten Änderungen vor, kompilieren und testen Sie manuell und führen Sie die Prüfung anschließend erneut aus.

Zuerst die Abdeckung prüfen

  • No Blueprint audit: der letzte normale Scan enthielt die optionale Prüfung nicht.
  • No Blueprints in scope: prüfen Sie die konfigurierten Analysebereiche und Ausschlüsse, falls Sie dies nicht erwartet haben.
  • Inspection failures: einige Assets konnten nicht gelesen werden; der Bericht deckt nur einen Teil der Assets ab.
  • Completed: die geplante Untersuchung und Analyse ist abgeschlossen. Das ist kein Nachweis der Kompatibilität mit einer Ziel-Engine.

Die Blueprint-Untersuchung wird nur auf Wunsch ausgeführt und lädt Assets aus dem Analysebereich in den Arbeitsspeicher. Sie liest ihren aktuellen Kompilierungsstatus im geladenen Zustand; sie startet keine Kompilierung, ändert keine übergeordnete Klasse, rekonstruiert oder löscht die Assets nicht und speichert sie nicht ausdrücklich. Das Laden durch die Engine kann den Zustand im Arbeitsspeicher beeinflussen. Die Prüfung speichert diesen Zustand nicht unbemerkt und setzt auch kein vorhandenes Änderungskennzeichen zurück.

Testen Sie die tatsächliche Engine-Migration in einer Projektkopie. Dieser Bericht findet aktuelle strukturelle Probleme und Hinweise zur Prüfung. Änderungen an der Engine-API und der Serialisierung, das C++-Verhalten und dynamisch geladene Referenzen müssen weiterhin in der Zielversion getestet werden.

Blockers kennzeichnet ein aktuelles Problem oder eine Lücke in der Vorbereitungsprüfung. Warnings enthält strukturelle Heuristiken, die eine Prüfung verdienen. Info nennt Anbieter, die für die Ziel-Engine überprüft werden sollten.

Die Kopplungsprüfung schließt Selbstreferenzen aus. Kopplungs- und Zyklusprüfungen verwenden direkte harte Verbindungen zwischen Blueprints im geprüften Analysebereich; weiche Verbindungen, Blueprints außerhalb des Analysebereichs und Verbindungen über andere Asset-Typen sind nicht Teil dieser Prüfungen. Native Klassen werden nicht als übergeordnete Blueprint-Klassen gezählt. Bei der Prüfung von Plugin-Anbietern werden auch native übergeordnete Klassen und Aufrufe untersucht.

Ein Schwellenwert ist ein Hinweis zur Prüfung und keine Kompatibilitätsgrenze. Passen Sie die Standardwerte in den Projekteinstellungen an Ihre Architektur an; Exporte halten die tatsächlich verwendeten Werte fest.

CSV- und JSON-Exporte

  1. Schließen Sie den Scan ab. Führen Sie zuerst die optionale Blueprint-Prüfung aus, wenn Sie Migrationsbefunde im Export benötigen.
  2. Verwenden Sie Export in der Kopfzeile oder Export CSV / Export JSON in Migration Audit.
  3. Lesen Sie den Exportpfad in der Oberfläche. Die Exportaktionen von Migration Audit kopieren diesen Pfad außerdem in die Zwischenablage.
  4. Die Dateien befinden sich unter <Project>/Saved/DependencyTracer/ oder im Verzeichnis, das mit Report Export Dir konfiguriert wurde.

Beide Formate exportieren den Scanbericht einschließlich seiner verfügbaren Prüfdaten. Ein Prüfexport enthält nicht nur die Zeilen, die unter dem aktuellen Such- oder Schweregradfilter sichtbar sind.

  • CSV: prüfen Sie die Berichtsabschnitte in einer Tabellenkalkulation oder geben Sie sie zur Prüfung weiter.
  • JSON: bewahren Sie einen strukturierten Snapshot für Vergleiche oder eigene Werkzeuge auf.

Die Migrationsdaten enthalten die Abdeckung, Befunde, Kennzahlen je Blueprint und die tatsächlich verwendeten Schwellenwerte. CSV enthält mehrere Berichtsabschnitte; JSON verwendet Schemaversion 1.0. Kein Export enthält den vollständigen Abhängigkeitsgraphen. Vergleichen Sie Berichte mit demselben Analysebereich und denselben Einstellungen; Änderungen am Analysebereich können Änderungen an Summen oder Befunden erklären.

Ein späterer normaler Scan ersetzt das Prüfergebnis durch einen Scan, dessen Prüfung deaktiviert ist. Bei Abbruch oder Fehler bleibt der vorherige abgeschlossene Bericht erhalten. Führen Sie nach dem erneuten Öffnen des Editors einen frischen Scan aus.

Fehlerbehebung

Dependency Tracer fehlt unter Tools

Aktivieren Sie das Plugin unter Edit > Plugins und starten Sie den Editor neu. Prüfen Sie, ob seine Deskriptordatei direkt im richtigen Plugin-Ordner liegt und das Paket zu Ihrer Engine-Version passt. Eine manuelle Quellcodeinstallation benötigt die zur Engine passende C++-Toolchain und einen erfolgreichen Editor-Build.

Der Scan ist leer oder ein Ordner fehlt

Prüfen Sie Analysis Roots und Excluded Folders. Verwenden Sie einen Paketpfad wie /Game/Characters. Aktivieren Sie Plugin-Inhalte, wenn diese zu Ihrem gewünschten Analysebereich gehören, und führen Sie anschließend einen frischen Scan aus.

Eine Größe ist unbekannt oder kleiner als erwartet

Speichern Sie das Asset und scannen Sie erneut. Das Ergebnis verwendet bekannte Paketgrößen auf dem Datenträger aus der Asset Registry. Nicht gespeicherte oder unbekannte Größen können ausgelassen werden; eine unvollständige Durchquerung kann eine Untergrenze ergeben. Die Ausgabe nach dem Cooking kann von gespeicherten Paketgrößen abweichen.

Mein ungenutzter Kandidat wird tatsächlich vom Spiel geladen

Prüfen Sie dynamische Pfade und externe Ladesysteme. Fügen Sie die betreffenden Ordner zu Additional Root Folders hinzu und scannen Sie erneut. Die Referenzanalyse kann nicht jeden zur Laufzeit auf Zeichenketten beruhenden Ladevorgang ableiten.

Die Abhängigkeitskarte zeigt alte Ergebnisse

Warten Sie, bis der neue Scan abgeschlossen ist, und klicken Sie anschließend auf Reload map. Prüfen Sie das ausgewählte Wurzel-Asset und den Filter für harte und weiche Referenzen. Anzeigegrenzen können Verbindungen auslassen; fokussieren Sie einen anderen Knoten, um weiter zu untersuchen.

Die Migrationsprüfung meldet, dass keine Prüfung ausgeführt wurde

Ein normaler Scan project untersucht keine Blueprint-Graphen. Öffnen Sie Migration Audit und verwenden Sie Run Blueprint Audit oder Scan + audit.

Eine Blueprint-Untersuchung ist fehlgeschlagen

Öffnen Sie das Asset manuell und prüfen Sie fehlende übergeordnete Klassen, Anbieter und Paketprobleme. Beheben Sie diese und führen Sie die Prüfung erneut aus. Bis dahin ist die Abdeckung unvollständig.

Es sind keine Befunde sichtbar

Leeren Sie die Suche und aktivieren Sie alle Schweregradfilter. Prüfen Sie die Anzahl untersuchter und gefundener Blueprints sowie den Analysebereich. Eine abgeschlossene Prüfung ohne Befunde bedeutet, dass ihre aktuellen Regeln keine gefunden haben; sie bestätigt nicht den Erfolg einer zukünftigen Engine-Migration.

Ein Bericht konnte nicht exportiert werden

Warten Sie, bis die Analyse abgeschlossen ist. Prüfen Sie das konfigurierte Ausgabeverzeichnis und die Schreibrechte und lesen Sie anschließend unter Window > Developer Tools > Output Log die Meldungen von Dependency Tracer.

Unreal meldet fehlende oder inkompatible Module

Wählen Sie das Archiv für die genaue Minor-Version der Engine und prüfen Sie, ob das Plugin mehrfach installiert ist. Quellcodepakete müssen mit einer kompatiblen C++-Toolchain gebaut werden. Verwenden Sie keine DLLs einer anderen Engine-Version in der Installation.

Häufige Fragen

Löscht oder überschreibt das Plugin meine Assets?

Unused Assets zeigt Kandidaten und Navigationsaktionen im Editor. Die Blueprint-Untersuchung lädt Assets, kompiliert oder speichert sie jedoch nicht ausdrücklich. Änderungen und Aufräumen gehören zu Ihrem gesonderten Prüfablauf.

Ist die angezeigte freigebbare Größe eine garantierte Speicherersparnis?

Sie entspricht der bekannten Paketgröße der zu prüfenden Kandidaten. Prüfen Sie ihre Verwendung, bevor Sie etwas löschen. Abhängigkeiten, Cooking und Komprimierung können beeinflussen, was ein ausgelieferter Build tatsächlich enthält.

Kann ich die Größen der größten Wurzel-Assets addieren?

Mehrere Wurzel-Assets können dieselben Abhängigkeiten teilen. Beim Addieren ihrer Gesamtgrößen werden diese gemeinsamen Pakete mehrfach gezählt; verwenden Sie die Summen nach Typ oder einen gemessenen Build für eine andere Betrachtung.

Garantiert eine Prüfung ohne Befunde eine erfolgreiche Migration?

Nein. Der Bericht prüft die aktuelle Blueprint-Struktur und den Status im geladenen Zustand. Validieren Sie eine Projektkopie in der tatsächlichen Ziel-Engine und testen Sie ihren C++-Code, die Anbieter, Inhalte und das Verhalten.

Ist der Bericht zur Migrationsvorbereitung enthalten?

Ja. Er ist in Dependency Tracer 1.1.0 neben den bestehenden Werkzeugen für Abhängigkeiten und Größen enthalten.

Benötigt mein gepacktes Spiel Dependency Tracer?

Das Modul des Plugins ist nur für den Editor bestimmt. Seine Untersuchungsoberfläche wird nicht im gepackten Spiel ausgeführt.

Benötigt die Analyse einen Onlinedienst?

Die Projektanalyse läuft lokal im Unreal Editor. CSV- und JSON-Berichte werden in das gewählte lokale Verzeichnis geschrieben.

Sind das Beispielprojekt und die Screenshots Teil meines Scans?

Die Screenshots zeigen ein eigens erstelltes Demonstrationsprojekt. Ihr Scan verwendet die von Ihnen konfigurierten Projekt-Assets. Die Beispielgrößen und Befunde dieser Anleitung sind keine vorgegebenen Ergebnisse, die in das Plugin eingefügt werden.

Version und Support

Diese Anleitung behandelt Dependency Tracer 1.1.0 für Unreal Engine 5.5, 5.6, 5.7 und 5.8 unter Windows 64-Bit.

In Version 1.1.0 enthalten

Die Project-Atlas-Oberfläche mit Abhängigkeitskarten und Inspektor, Verbindungen für harte und weiche Referenzen, Untersuchung ungenutzter Inhalte, Größenberichte nach Wurzel-Assets und Typen, CSV-/JSON-Export und der Blueprint Migration Readiness Report.

Die Engine-Kompatibilität wurde mit UE 5.5.4, 5.6.1, 5.7.4 und 5.8.0 unter Win64 geprüft. Die Ausführung unter Mac und Linux wurde in der Validierungsumgebung dieser Version nicht überprüft.

Ein Problem melden

Kontaktieren Sie nexusforgeuesupport@gmail.com.

Geben Sie Ihre Unreal-Engine- und Plugin-Versionen, den ausgewählten Tab, die Analysebereiche und Ausschlüsse, die genaue Meldung sowie Schritte zur Reproduktion des Problems an. Bei einem Graphenproblem fügen Sie den Filter für harte und weiche Referenzen und einen Screenshot in voller Größe bei. Bei einem Prüfproblem nennen Sie die Regel-ID und die Abdeckung.

Teilen Sie nur die relevanten Teile von Berichten und Protokollen; sie können Asset-Pfade und Namen aus dem Projekt enthalten.
